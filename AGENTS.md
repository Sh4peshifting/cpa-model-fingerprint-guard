# AGENTS.md

## Project purpose

Develop `model-fingerprint-guard`, a standalone plugin for CLIProxyAPI that detects suspected upstream model substitution using lm-detector's three-challenge random-number fingerprinting method. It must support periodic idle checks, error-triggered checks, per-auth controls, temporary routing isolation, confirmed-mismatch disabling, durable audit records, and a built-in management UI.

Upstream references:

- CLIProxyAPI: https://github.com/router-for-me/CLIProxyAPI
- lm-detector: https://github.com/Ikaleio/lm-detector
- CLIProxyAPI management center: https://github.com/router-for-me/Cli-Proxy-API-Management-Center

The user's explicit requirements take precedence over defaults or implementation suggestions in this file. Treat examples of APIs, field names, models, and configuration from planning conversations as proposals until verified against the pinned upstream source.

Prefer a small, maintainable embedded frontend; React, TypeScript, and Vite are acceptable if justified. - Keep code modular, explicit, and testable. Separate host adapter, configuration, event ingestion, auth policy, scheduler, quarantine, fingerprint engine, persistence, management API, and UI. Use interfaces at dependency boundaries, context cancellation, injectable clocks, and deterministic fakes. Avoid unnecessary dependencies, speculative abstractions, and unrelated refactors.

## Functional requirements and invariants

### Configuration and per-auth policy

- Support a global guard enable flag, provider defaults, and per-auth overrides. A disabled global guard overrides lower-level settings. Per-auth settings may independently enable fingerprint checks, idle checks, and error-triggered checks and choose the request model and expected fingerprint model.
- Keep fingerprint-check enablement separate from the host's actual auth `disabled` flag. Turning off fingerprint checking must not disable an otherwise healthy auth or reactivate an auth disabled by an administrator or a confirmed mismatch.
- Support configurable scan interval, minimum idle duration, minimum interval between checks, test model and expected-model mapping, timeouts, concurrency, error triggers, minimum valid-match score/confidence if exposed by the SDK, mismatch confirmation rounds, retry/backoff, and quarantine expiry policy. Validate all config, reject invalid values, and document precedence and defaults.
- Prefer stable Auth IDs for state and identity. Resolve filenames/provider names explicitly; do not assume filenames are globally unique. Persist configuration and apply changes without restarting the host where supported. Cancel or safely reconcile obsolete jobs when policies, auth contents, or configuration change.

### Idle checks and error events

- A periodic scan should check eligible enabled auths that have had no ordinary business request for the configured idle duration and are due for another check. Track business activity at the correct lifecycle stage, including failed attempts and active streams. Do not treat probe traffic as business activity. Do not infer that an auth is idle when active-request or last-use data is unknown; use a conservative startup policy and document any host telemetry limitations.
- For each protected auth, detect upstream HTTP 502, HTTP 503, `server_is_overloaded`, and `Our servers are currently overloaded. Please try again later.` (configurable substring matching is acceptable). Cover structured error bodies and SSE error events, including HTTP 200 streams carrying an error, where the host exposes them. Attribute errors to the actual attempted Auth ID, not merely the final client response or request model. Do not treat the proxy's own unrelated errors as upstream auth failures.
- On a matching business error, immediately quarantine that auth for new ordinary requests and enqueue a high-priority fingerprint check without waiting for the idle threshold or regular check interval. Require one trigger by default; support configurable deduplication and thresholds. Existing in-flight requests need not be forcibly cancelled.
- Ensure single-flight checks per auth, bounded global/provider concurrency, jitter, and backoff. Distinguish internal probe requests from ordinary traffic so probes cannot recursively trigger quarantine or reset idle timers. Handle global/provider overload without creating a probe storm.

### Routing isolation and diagnostic execution

- Temporary quarantine is NOT the same as persistent auth disabling. Quarantined auths must be excluded from ordinary routing while remaining available to an explicitly targeted diagnostic request. Never briefly re-enable a persistently disabled auth merely to run a probe.
- Verify quarantine coverage across relevant routing paths, models, retries, streaming, and candidate selection. An error-triggered quarantine should take effect before the next new dispatch whenever the host supports a synchronous hook. If only asynchronous events exist, document the race and exact guarantee; do not advertise atomic isolation.
- Use host-supported execution to pin every fingerprint challenge to the same exact Auth ID and intended request model, including retries. Never use general load-balanced requests or allow fallback to another auth, provider, or model. If strict pinning cannot be verified, mark the check unsupported/invalid, never mismatch.
- Verify host cooldown behavior after 502/503. Prefer a supported diagnostic-only execution path that can bypass the relevant transient overload cooldown without bypassing manual disabling, security checks, or real quota constraints. Do not indiscriminately clear quota state or global cooldown. If no safe bypass exists, report the limitation and retry at the earliest allowed time; any necessary minimal host patch must be explicit and separately reviewable.

### Fingerprint detection and decisions

- Reuse lm-detector's actual three-challenge protocol, reference data, feature extraction, scoring, and validation. Read and test the pinned implementation. Do not invent or loosely approximate its prompts, random-number rules, or classifier. Preserve SDK/reference-data licenses and attribution.
- Complete a full valid three-challenge round against the same auth and model. Validate all outputs using the SDK. Use local inference of fingerprints where supported; never send auth secrets or raw auth files to a third-party detection service.
- Distinguish request-model names from canonical expected reference-model labels. For error-triggered checks, prefer the failed model when configured and supported; otherwise use an explicitly configured test model and label the result as limited to that model. Never infer that a different tested model establishes the failed model's identity.
- Represent results as match, confirmed mismatch, inconclusive, unsupported, transient failure, or cancellation. Only a valid, sufficiently strong, reference-supported mismatch satisfying the configured confirmation policy may cause permanent disabling. Allow one full valid round to trigger disabling when configured; additional confirmation rounds are optional. Use the SDK's real score semantics; do not present an arbitrary similarity score as a calibrated probability of model identity.
- On match, release plugin quarantine and resume normal host-managed routing if the auth remains eligible. On confirmed mismatch, disable the auth through a verified host-supported mechanism and persist the abnormal timestamp and evidence. On overload, timeout, rate limit, invalid samples, unsupported reference, or inconclusive result, never declare a mismatch or permanently disable automatically; follow a documented retry/quarantine policy. Default expiry must not silently release an unresolved quarantined auth: retain isolation and require operator action unless an explicit policy permits release.
- Respect manual disable, deletion, credential replacement, and config changes. Do not apply a stale result to a changed auth. A plugin-generated disable must remain in effect across restart until explicitly recovered by an authorized operator; recovery must not overwrite an unrelated manual disable.

### State and persistence

- Use separate durable operational state for last business activity, last check, first trigger, quarantine, retry, last result, confirmation count, and history as needed. Restore unresolved quarantine before admitting new business routing where the host supports that ordering. If startup ordering cannot guarantee it, document the limitation. Use bounded history and retention settings.
- On confirmed mismatch, update the original auth file or its authoritative host-backed auth record using supported APIs. Persist `disabled: true` (or the exact host equivalent), a namespaced structured plugin record, the confirmed abnormal time, disable time, expected/detected model, trigger reason/time, and validated result details. Add a concise human-readable abnormal-time marker to the existing note when supported; preserve user-authored notes. Do not confuse the trigger time with the confirmed-mismatch time.
- Preserve unrelated auth fields, OAuth token refreshes, permissions, and storage semantics. Use host concurrency/transaction mechanisms if available; otherwise use a conservative read-modify-write strategy with conflict detection. Never overwrite credentials with a stale snapshot. Verify both persistent and runtime disable state; reconcile partial failures and never report success prematurely.
- Store timestamps in RFC 3339 with timezone (prefer UTC); display in the UI's local timezone. Avoid logging prompts/responses containing secrets, tokens, management keys, full auth files, or sensitive upstream bodies. Sanitize and limit error excerpts and audit records.

## Management UI and API

- Provide a native-discoverable plugin management page/menu when supported by the verified host and management-center version. Prefer official plugin extension mechanisms, embedded static assets, and authenticated management routes. Do not require a separate Node.js server, frontend container, or new port at runtime if host capabilities permit it.
- Include overview, auth management, detection settings, and history. Show total/protected/quarantined/disabled counts, current per-auth state, last business activity, last check/result, trigger and confirmed abnormal times, and useful errors. Offer search/filter, per-auth enable/disable, separate idle/error toggles, model mapping, manual check, bulk enable/disable and bounded batch checks, and explicit authorized release/recovery actions.
- Show global/provider/per-auth precedence and validation errors. Expose all supported scheduling, trigger, fingerprint, concurrency, and recovery options. Do not render a control for functionality that is not implemented; clearly label unsupported features. Provide loading, empty, error, and success states and confirm destructive or bulk actions. Refresh status while jobs run; use real API results, not static mock success.
- Read/write config through validated management APIs with durable storage and hot reload when supported. Enforce authentication and authorization on every sensitive endpoint, including reads of auth metadata and history. Public resource routes may serve static UI only. Never embed or expose management credentials or provider tokens. Escape untrusted upstream text and avoid XSS, insecure cross-origin access, and credential leakage. Do not log secret headers or query parameters.
- Provide a Simplified Chinese UI and user-facing setup documentation; keep naming and code conventions consistent. Ensure the frontend production build works with the plugin's actual resource base path and is embedded in the release artifact.

## Testing and acceptance

- Add tests with every functional slice. Use table-driven Go tests, fake host callbacks, a fake clock, fake fingerprint results, and controlled upstream/SSE fixtures. Prefer reproducible offline tests; do not use real credentials, paid requests, or production accounts by default.
- Cover config validation and precedence, per-auth toggles, idle scheduling, active streaming, all trigger patterns, HTTP/SSE distinction, exact auth/model pinning with no fallback, isolation across normal routing and retries, native cooldown interactions, match/mismatch/inconclusive handling, repeated errors, probe recursion, retry backoff, concurrency, manual disable, auth replacement/deletion, config reload, restart recovery, persistence failure, and concurrent token updates.
- Test that a 502/503 on auth A does not quarantine auth B; that ordinary routing excludes A while diagnostic traffic targets A; that a valid match releases only the plugin's quarantine; and that a confirmed mismatch both persists and enforces disabling with the correct timestamp. Verify that an unavailable or unsupported model is not falsely disabled.
- Test management authentication, config validation, UI actions, and absence of credential leakage. Run frontend typecheck, lint, tests, and production build when applicable. Include an integration test against the pinned CLIProxyAPI version or a reproducible host harness. An interface-only mock is not sufficient evidence of real host routing, cooldown bypass, or lifecycle semantics.
- Run `gofmt` on changed Go files, `go test ./...`, `go vet ./...`, and `go test -race ./...` on supported platforms where feasible. Run existing project checks and a plugin release build. Verify generated artifacts, dependencies, and Git diffs. If a check cannot run, record the exact reason and scope; never claim it passed.
- Before delivery, provide installation/upgrade/uninstall instructions, sample configuration, management UI entry path, compatibility/version constraints, build commands, tests actually run, known limitations, and a Git commit summary. Never claim a binary or feature is tested when it is not.

## Git discipline (mandatory)

Use Git throughout development, not as a single final checkpoint.

- Make small, coherent, independently reviewable commits as implementation milestones are completed. Each commit should address one logical change, include its related tests/docs, and leave the project buildable whenever feasible. There is no arbitrary line-count target: split unrelated changes, not meaningful atomic changes. Do not accumulate all features into one commit or make meaningless commits solely to increase the count.
- Follow Conventional Commits: `type(scope): concise imperative summary`, such as `feat(config): validate per-auth fingerprint policy`, `test(routing): cover quarantine and exact auth pinning`, or `fix(auth): preserve refreshed credentials on disable`. Use `feat`, `fix`, `test`, `refactor`, `docs`, `build`, `ci`, or `chore` as appropriate. Explain non-obvious decisions or breaking changes in the commit body.
- Inspect `git status --short`, `git diff`, and `git diff --cached` before each commit. Stage explicit files or selected hunks; avoid broad staging when unrelated edits exist. Run the relevant tests and `git diff --check` before committing. Commit only changes made or explicitly authorized for this task. Do not stage, discard, or amend pre-existing user changes.
- Commit source, tests, reproducible build scripts, required lockfiles, and documentation. Ignore real auth files, `.env` secrets, tokens, credentials, private keys, local databases/logs, build artifacts, dependency directories, and temporary files. Use sanitized fixtures. Do not commit vendored dependencies, compiled plugins, or generated frontend bundles unless the established release/build process explicitly requires them. Check staged contents for secrets before committing.
- Never force-push, rewrite existing history, run destructive reset/clean commands, bypass hooks, or push to a remote without explicit user authorization. Do not invent commits or report commits that were not created. If Git identity or permissions block commits, report the exact problem rather than overriding the user's global Git config.
- Prefer an incremental sequence such as: (1) project scaffolding, pinned dependencies, verified host compatibility notes and `.gitignore`; (2) configuration and per-auth policy; (3) state and idle scheduling; (4) error events and quarantine; (5) pinned execution and fingerprint checks; (6) result handling and durable disable/metadata; (7) management APIs; (8) embedded UI and integration; (9) end-to-end tests, packaging and documentation. Adapt or split this sequence to the actual dependency graph; do not postpone all tests until the final commit.
- End with `git status --short` and `git log --oneline` (or the appropriate branch range) and report remaining changes and actual test outcomes. Keep the working tree clean of agent-created uncommitted changes when possible; preserve unrelated user changes.
